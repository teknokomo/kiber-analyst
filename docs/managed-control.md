# Управляемый контроль источников

Этот интерфейс предназначен для restricted SSH-клиента, который вызывает
только фиксированные операции брокера. Он не предоставляет shell, произвольные
пути, SQL, доступ к PostgreSQL, конфигурации провайдеров или секретам.

## Область проектов

Брокер читает операторскую политику `project-access.json` из каталога
конфигурации сервиса. Образец находится в
[`config/project-access.example.json`](../config/project-access.example.json).
Политика должна принадлежать root, быть доступна сервису на чтение и не быть
доступной для записи группе или остальным пользователям. Список
`authorized_projects` содержит существующие проекты, к которым оператор
разрешил доступ этому restricted principal. Проекты из операторского
`sources.json` также разрешены для совместимости со статическими источниками.
По умолчанию список пуст и создание проектов выключено. Broker загружает
политику при запуске; после изменения `project-access.json` или `sources.json`
нужен штатный рестарт broker.

`project-list` показывает только разрешённые проекты, реально существующие в
knowledge. `project-create SLUG "Название"` доступна, только если
`allow_project_create=true`. Новые проекты помечаются владельцем и ключом
идемпотентности в `projects.meta`; существующий проект без этой метки нельзя
присвоить повторной командой. Брокер сохраняет собственный grant для созданного
проекта. Он не переносит и не объединяет существующие данные.

Любая команда, связанная с заявкой, повторно проверяет доступ к проекту из её
фиксированных параметров. Отзыв доступа к созданному через broker проекту
выполняет оператор; отдельной команды отзыва у restricted клиента нет.
Заявки при отзыве не удаляются.

## Операции

В текущем интерфейсе доступны только реализованные коннекторы GitHub, GitLab,
GitVerse и Telegram. Любой источник должен быть корректным `source_id`, а
проект — разрешённым. Коннекторы GitHub/GitLab/GitVerse дополнительно проверяют
доступность API-хоста по своей операторской конфигурации до отправки токена.
Регистрация источника сама по себе не подтверждает доступ: для этого служит
provider dry-run.

Примеры команд restricted клиента:

```text
capabilities
project-list
project-create example-project "Example project"
source-list [PROJECT]
source-add SOURCE_ID PROJECT
source-status SOURCE_ID PROJECT
ingest-dry-run SOURCE_ID PROJECT YYYY-MM-DD [LIMIT]
ingest SOURCE_ID PROJECT [SINCE]
embed SOURCE_ID PROJECT
job-list [source_id=SOURCE_ID] [status=STATE]
job-status REQUEST_ID
job-logs REQUEST_ID [N]
retry REQUEST_ID
cancel REQUEST_ID
search-source SOURCE_ID PROJECT "поисковый запрос" [LIMIT]
search-project PROJECT "поисковый запрос" [LIMIT]
```

Для обоих поисковых команд допустим `LIMIT` от 1 до 50; отсутствие значения
использует 5. Запрос с пробелами передавайте одним аргументом в кавычках.

В первом внешнем ingest передавайте явную раннюю дату и сначала выполняйте
`ingest-dry-run`. Dry-run загружает данные провайдера, исполняет транзакцию
загрузки и подтверждает откат. Он не означает полный результат, если в отчёте
есть `partial_reasons`. После успешного реального ingest `embed` обрабатывает
текущий проект и источник через штатную очередь. Повтор активной одинаковой
команды возвращает существующую заявку; конфликтующие параметры для активного
источника отклоняются. `retry` разрешён только для временной ошибки и в рамках
лимита попыток. Результат/прогресс читается через `job-status` и
`source-status`.

Для Telegram управляемый импорт сейчас поддерживает отдельную тему, не весь
чат как единый источник. `source-add` проверяет полный, неограниченный экспорт
темы с
совпадающими `source_id`, манифестами и SHA-256 в фиксированном каталоге
импортов. Затем доступны dry-run, ingest, embedding, status и search. Сам
экспорт запускается отдельным ограниченным интерфейсом;
Kiber broker не читает Telegram-сессию и не вызывает экспортёр. Не копируйте
Telegram-сессию между службами. Если export-команда отсутствует в доступном
restricted канале, запросите включение export-операции в соответствующий
ограниченный интерфейс; не подменяйте экспорт произвольным shell.

`source-status` возвращает только агрегаты и последние request/job IDs. Для
текущей модели embeddings в счётчиках отдельно показываются число непустых
элементов без вектора. `search-source` ограничивает результаты выбранным
источником; `search-project` ограничивает их разрешённым проектом. Результаты
содержат только явные поля provenance и ограниченный фрагмент текста.

Не реализованные коннекторы (например, веб-страницы и произвольные документы)
не считаются доступными. Список `capabilities` отражает это явно.

## Проверка и развёртывание

Публикуемая конфигурация является только примером и не содержит реальных
project slug. На сервере оператор должен создать root-owned `project-access.json`,
указать только принадлежащие владельцу или явно делегированные проекты и
включить создание новых проектов отдельным флагом. Restricted SSH-wrapper
должен разрешать только перечисленные команды, проверять число аргументов и
передавать их фиксированному broker-client. Сам broker повторно проверяет
project grants и состояния заявок.

Эта документация описывает контракт пакета. Она не означает, что новая версия
broker или SSH-wrapper уже установлена на сервере.
