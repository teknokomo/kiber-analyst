# Queue v4: согласованное обновление и откат

Этот runbook относится к SQLite-очереди Kiber-analyst. Обновление worker и
broker выполняется как одна версия протокола и схемы. Совместимость worker
или broker из релиза 0.2.0 с queue v4 не доказана: запускать старый компонент
на очереди v4 запрещено. MCP и база knowledge не являются частью миграции
очереди; для них требуется отдельный план, если их версия меняется.

## Перед обновлением

1. Согласовать окно обслуживания и временно запретить новые `submit` и broker
   mutations. Дождаться завершения задач или зафиксировать каждую активную
   задачу вместе с её состоянием, checkpoint, attempts и последним событием.
   Не останавливать активные задачи без отдельного согласованного плана.
2. Записать build-id/commit и версии worker и broker, SQLite `user_version`,
   список job ID/state/operation, прогресс и очередь ожидания. Секреты и
   содержимое env-файлов в отчёт не включать.
3. Сохранить код, units и конфигурацию broker/worker как один rollback-набор.
   Также сделать SQLite Backup API backup broker `requests.sqlite3` после
   остановки broker. Закрытые env-файлы копировать только в защищённое
   хранилище с исходными владельцем и режимом; в журнале оставить только
   имена файлов, права и контрольные суммы, не значения.
4. Пока старый worker ещё работает на исходной схеме, создать pre-upgrade
   backup очереди через `kiber-analyst-queue-backup` или worker control
   action `backup` с `pre_upgrade=true` от root. Не вызывать backup через
   уже обновлённый worker: его старт автоматически мигрирует очередь.
   Не копировать активный `queue.db` обычным `cp`: WAL может содержать
   подтверждённые транзакции.
5. Проверить оба SQLite backup: SHA-256; `PRAGMA integrity_check` = `ok`;
   ожидаемые schema versions; восстановление копии в отдельный scratch-каталог;
   совпадение набора job/request IDs и контрольных полей с инвентарём до
   обновления. Не запускать worker на production-очереди до прохождения этой проверки.

## Обновление

1. Остановить приём новых broker-команд и штатно остановить broker и worker.
   Убедиться, что оба процесса завершились и больше не держат очередь.
2. Установить один и тот же проверенный build для worker и broker, пока оба
   остановлены. Запуск нового worker выполняет предусмотренную миграцию queue
   v3 → v4. Не оставлять старый broker с новым worker или наоборот: разные
   версии могут иметь несовместимые protocol и схему. Если нельзя подтвердить
   одинаковый build и поддержку v4 обоими компонентами, не запускать ни один.
3. Запустить worker, проверить build-id, `user_version=4`, целостность БД,
   отсутствие stuck jobs и сохранность инвентаря. Затем запустить broker той
   же версии и проверить его обычные read/status операции. Возобновить приём
   команд только после обоих проверок.
4. Сопоставить до/после job ID, состояние, operation, checkpoint, attempts и
   следующий запуск. Миграция не должна терять или повторно запускать jobs.

## Откат

1. Снова закрыть приём команд и остановить broker и worker. Никогда не
   подключать worker 0.2.0 к queue v4.
2. Сначала сохранить post-upgrade backup и инвентарь всех jobs, созданных или
   изменённых после pre-upgrade backup. Установить согласованные версии кода,
   units и конфигурации из rollback-набора.
3. Восстановление pre-upgrade backup заменит текущее состояние очереди.
   Поэтому jobs, созданные после снимка, исчезнут из восстановленной БД.
   До отката их нужно перечислить и сверить с артефактами и внешними
   результатами. После восстановления каждую задачу вручную классифицировать:
   завершённую — отметить в операторском журнале; незавершённую с доказанным
   checkpoint — поставить заново с теми же параметрами; попытку с
   неопределённым внешним исходом не отправлять повторно, пока не проверены
   провайдер и сохранённые результаты. Автоматически проигрывать все
   post-backup jobs нельзя.
4. Восстановить backup через штатный queue-restore/SQLite Backup API,
   проверить checksum, `integrity_check`, schema version и инвентарь jobs.
   Если откат к старому worker требует схему старее v4, восстановить
   совместимый pre-upgrade backup целиком; не понижать `user_version` вручную
   и не запускать старый worker на новой схеме.
5. Запустить worker и broker только согласованной парой, сверить очередь,
   затем открыть приём команд. Сохранить оба backup-набора и журнал
   reconciliation до отдельного подтверждения их удаления.

Выпуск этого runbook или успешная локальная проверка не являются разрешением
на production-деплой и не подтверждают совместимость старых runtime.
