# Экспорт и передача Telegram

Kiber-analyst включает ограниченный по интерфейсу экспортёр Telegram и
издатель готовых экспортов. Они устанавливаются из того же пакета, что и
импортёр. Проверенный CLI-интерфейс — **Better-TG-CLI v0.41.2**
([release](https://github.com/TheVilfer/better-tg-cli/releases/tag/v0.41.2));
требуется Node.js 20 или новее. Установите зафиксированную совместимую версию:

```bash
npm install --global better-tg-cli@0.41.2
TELEGRAM_CLI="$(command -v telegram)"
"$TELEGRAM_CLI" --version
```

Проверенный релиз предоставляет используемые команды `info`, `read --limit
--full --json`, `--before`, `--topic`, raw `api`, `messages
get-forum-topics-by-id` и `download --output --json`. Kiber-analyst запускает
их фиксированным argv, ограничивает время, stdout/stderr и размер каждого
файла. Другие версии CLI не считаются совместимыми, пока оператор не сверит
эти интерфейсы. Экспортёр использует локально авторизованный профиль; пакет не
переносит Telegram-сессию, credentials или историю между серверами.

## Установка

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
pip install .
kiber-analyst-telegram-export --help
kiber-analyst-telegram-publish --help
```

Команды работают в Linux, используют стандартную библиотеку и не требуют
новой Python-зависимости. Войдите в Telegram от имени выделенного Unix
пользователя. Доступные группы, темы и история ограничены членством и правами
этого Telegram-аккаунта. Не копируйте его каталог авторизации.

Выделенный пользователь должен владеть export root, CLI home и деревом данных;
каталоги данных имеют режим `0700`, файлы — `0600`. В `telegram_cli` укажите
абсолютный путь к найденному исполняемому файлу, а не имя из интерактивного
`PATH`. Экспортёр передаёт дочернему процессу только `PATH=/usr/bin:/bin`,
поэтому Node.js должен находиться в одном из этих каталогов. Для стандартной
установки экспортёр и издатель запускаются одним выделенным пользователем.
Разделение exporter и publisher между разными Unix-пользователями этой версией
не поддерживается; изменять владельцев отдельно для такого режима нельзя.

Скопируйте примеры из [`config/`](../config/telegram-export.example.json) в
локальный конфигурационный каталог и замените значения путей, UID/GID и
квоты для своей системы. Файлы конфигурации не содержат Telegram-сессию или
секреты. Exporter config должен иметь режим `0640`, владельца `source_uid` и
группу `source_gid`, заданные publisher. Exporter также принимает этот режим;
`0600` publisher не принимает даже при общем владельце. Publisher config имеет режим `0600`;
родительские каталоги не должны быть доступны на запись посторонним. Пример
publisher config ссылается на фактический
exporter config, поэтому `storage_limit_bytes` и `min_free_bytes` в обоих
файлах должны совпадать. `expected_data_uuid=null` и `require_mount=false`
подходят только для тестового локального дерева. Для отдельного тома задайте
UUID и включите проверку монтирования.

## Экспорт группы или темы

```bash
export KIBER_TELEGRAM_EXPORT_CONFIG=/absolute/path/telegram-export.json
kiber-analyst-telegram-export export CHAT_ID GROUP MEDIA 100
kiber-analyst-telegram-export export-services CHAT_ID GROUP
kiber-analyst-telegram-export export-status CHAT_ID GROUP
kiber-analyst-telegram-export export-transfer CHAT_ID GROUP
kiber-analyst-telegram-export export-transfer-status CHAT_ID GROUP
```

`GROUP` экспортирует всю доступную историю обычной группы или форумной
супергруппы со всеми её темами. Для отдельной темы форумной группы передайте
числовой ID вместо `GROUP`:

```bash
kiber-analyst-telegram-export export CHAT_ID TOPIC_ID MEDIA 100
kiber-analyst-telegram-export export-services CHAT_ID TOPIC_ID
kiber-analyst-telegram-export export-status CHAT_ID TOPIC_ID
kiber-analyst-telegram-export export-transfer CHAT_ID TOPIC_ID
```

Это разные scope и source ID: `telegram:<chat_id>:group` и
`telegram:<chat_id>:topic:<topic_id>`. Экспорт сохраняет scope и происхождение
каждого сообщения и события. Успешный экспорт включает доступную аккаунту
историю; недоступные события отражаются в `limitations`. Сообщения и служебные
события экспортируются отдельно, каждый файл имеет собственный manifest и
SHA-256.

Для форум-группы Telegram помечает `forum_topic` в `messageReplyHeader` для
сообщений не из General; `reply_to_top_id` задаёт ID сообщения, начавшего
тред. Better-TG-CLI v0.41.2 также выдаёт `topicId` при чтении всей истории
форума, но это поле может быть производным: при отсутствии `topMsgId` CLI
подставляет ID ответа или `1`. Поэтому экспортёр определяет принадлежность
по исходному `forumTopic` и `topMsgId`, а не считает производный `topicId`
доказательством. General (отсутствующий или ложный optional-флаг
`forumTopic`) записывается как известная тема `1`, даже если у ответа есть
`topMsgId`. Если `forumTopic=true`, но надёжного `topMsgId` нет,
принадлежность сохраняется как `topic_id=null` и
`topic_id_status=unknown`; message ID ответа при этом сохраняется для будущей
сверки, а manifest показывает число неопределённых сообщений. Автоматическое
уточнение таких записей пока не выполняется, и их нельзя считать корректно
отнесёнными к теме до сверки. См.
[Telegram messageReplyHeader](https://core.telegram.org/constructor/messageReplyHeader).

У `messageActionTopicCreate` нет поля с topic ID: действие содержит название и
параметры значка. При экспорте всех служебных событий форума создание темы
остаётся `topic_id=null` / `unknown`, если API не даёт совпадающий
`replyToTopId`; оно не приписывается General по умолчанию. При экспорте одной
темы событие принимается только при точном совпадении ID события с запрошенным
topic ID либо при совпадающем `replyToTopId`. Противоречащий корень делает
принадлежность неизвестной, и событие не включается в конкретную тему. См.
[Telegram messageActionTopicCreate](https://core.telegram.org/constructor/messageActionTopicCreate)
и [ForumTopic](https://core.telegram.org/constructor/forumTopic).

Аргументы `export` после `MEDIA`:

```text
export CHAT TOPIC MEDIA [PAGE_LIMIT] [BEFORE] [MAX_FILE_SIZE]
```

`MAX_FILE_SIZE` можно передать, например, как `100MiB`, `4000MB` или
`4000000000B`. По умолчанию это `100 MiB = 104857600` байт; максимум
`4000 MB = 4000000000` байт (десятичные MB). Флаг `MEDIA` включает файлы всех
поддерживаемых типов вложений Telegram, а не только аудио. Предел относится к
каждому файлу отдельно. Выбранное значение, число скачанных и пропущенных
файлов, размер и источник размера, SHA-256 и причина пропуска отражаются в
manifest/status. Поддерживаются только вложения, которые Telegram CLI может
выдать через свою download-команду; необнаруженный или нескачиваемый объект
отдельно отмечается причиной.

Для длинной истории manifest хранит точный `skipped_media_count`, сводку
`skipped_media_by_reason` и не более 100 безопасных примеров в
`skipped_media`; `skipped_media_sample_truncated` показывает, когда список
примеров ограничен. Причина и размер каждого вложения остаются в его строке
`messages.jsonl`, поэтому manifest не растёт вместе с числом пропусков. Вывод
Telegram CLI ограничен 32 MiB для stdout и 256 KiB для stderr; превышение
завершает весь дочерний процесс и не сохраняет неограниченный вывод.

Экспорт потоковый: файл не целиком загружается в память. Перед загрузкой
проверяются доступное место, общий лимит хранилища и оставленный резерв;
поток ограничивается выбранным лимитом и системным `RLIMIT_FSIZE`. При
прерывании текущий неполный файл удаляется и может быть безопасно загружен
заново, завершённые файлы и страницы остаются. Это не обещает докачку с
байтового смещения: используемый Telegram CLI не предоставляет проверенную
здесь команду range-resume.

Для возобновления/позднего повышения лимита используйте:

```bash
kiber-analyst-telegram-export export-resume CHAT_ID GROUP 4000MB
kiber-analyst-telegram-export export-status CHAT_ID GROUP
kiber-analyst-telegram-export export-transfer CHAT_ID GROUP
```

`export-resume` принимает новый лимит от `100MiB` по умолчанию до `4000MB`.
Оно не перезаписывает `messages.jsonl`, `services.jsonl`, обычный manifest,
служебный manifest, уже выгруженные сообщения и события. Данные resume хранятся
в отдельной приватной области с checkpoint, SHA-256 и причиной каждого
пропуска. `export-transfer` проверяет исходный scope, manifests, контрольные
суммы и файлы; publisher атомарно выпускает новую staging-ревизию. Новая
ревизия обязана включать все файлы прошлой ревизии без изменения их пути,
размера и SHA-256. Предыдущий staging snapshot сохраняется под `.revisions/`.
При несовместимом или неполном snapshot передача прекращается с безопасным
кодом ошибки, не заменяя текущую ревизию.

При явном уменьшении лимита exporter заново проверяет фактический размер и
SHA-256 каждого сохранённого receipt в обоих корнях (`media/` и
`media-resume/`). Если хотя бы один файл больше нового лимита, команда
возвращает `RESUME_LIMIT_BELOW_EXISTING_MEDIA` до изменения checkpoint и
manifest. Существующие файлы и готовый staging snapshot остаются без изменений;
команда не сообщает `complete`. Если все файлы укладываются в новый лимит,
receipt и manifest получают новый предел без перезаписи самих файлов, после
чего publisher проверяет и принимает новую ревизию.

Текущий publisher допускает только добавочные media-ревизии. Поэтому нельзя
безопасно понизить предел для той же staging-ревизии, если это потребовало бы
исключить уже опубликованный файл сверх нового лимита: удаление или молчаливое
исключение нарушило бы контракт сохранности. Для такого изменения оператор
может подготовить новый полный экспорт в отдельном настроенном `export_root`
и отдельном `destination_root`, выбрав новый предел при экспорте. Старые
экспорт и staging остаются на месте; новый пакет публикуется и проходит
проверку source ID, scope, полноты и хешей отдельно. Переключать реестр источника
на новую staging-область следует только после успешной проверки dry-run и
сверки данных. Если отдельная staging-область не настроена, оставьте текущую
ревизию без изменений: `export-resume` не выполняет такой cutover сам.

Receipt checkpoint v1/v2 может ссылаться на `media/<message_id>/<file>` или
`media-resume/<message_id>/<file>`. Broker принимает только эти два корня,
проверяет размер и SHA-256 исходного файла и сохраняет тот же относительный
путь в неизменяемой staging-ревизии; произвольные пути отклоняются.

Повтор `export-transfer` под эксклюзивной блокировкой проверяет оставшиеся
временные кандидаты. Частичный каталог удаляется только при совпадении
source-bound intent/marker и проверенных правах; завершённый старый кандидат
переносится в `.revisions/recovery-*`. Ответ publisher содержит
`recovery_cleanup` с числом удалённых артефактов, освобождёнными байтами,
числом сохранённых кандидатов и причинами сохранения. Уже готовые `.revisions`,
данные других источников, оригинальный экспорт и артефакты с неизвестным
происхождением не удаляются. Неизвестный init-каталог останавливает передачу
с `TRANSFER_RECOVERY_REQUIRED`; сначала требуется ручная проверка.

`export-transfer` без `sudo` вызывает publisher по абсолютному пути из
защищённой конфигурации. Протокол publisher принимает только одну фиксированную
операцию (`budget`, `copy` или `status`) и `source_id`; произвольные команды и
пути через него не передаются.

## Регистрация, dry-run и ingest

Publisher размещает готовый topic package по настроенному фиксированному пути
импорта. Затем используйте установленный restricted broker/CLI Kiber-analyst
и разрешённый project grant:

```text
source-add telegram:<CHAT_ID>:group <PROJECT>
ingest-dry-run telegram:<CHAT_ID>:group <PROJECT> 2000-01-01
ingest telegram:<CHAT_ID>:group <PROJECT>
job-status <REQUEST_ID>
```

Для отдельной темы замените source ID на
`telegram:<CHAT_ID>:topic:<TOPIC_ID>`. В БД внешний ID сообщения имеет вид
`tg:<chat_id>:<message_id>`, поэтому пересекающиеся scope (например, вся группа
и входящая в неё тема) нельзя импортировать в один проект; то же сообщение
нельзя перепривязать к другому проекту. Система не перемещает и не объединяет
уже загруженные данные. Разделение overlapping scope потребует отдельной
миграции модели идентичности сегментов. Несовпадающие темы могут храниться
отдельно, когда их external references не пересекаются.

До первого реального ingest проверьте `source_id`, source/project grants,
завершённость обоих manifest, SHA-256 и отчёт dry-run с
`rollback_confirmed=true`. Ingest повторно проверяет файлы по dirfd, запрещает
symlink/traversal и сверяет размер, хеш и лимит каждого файла потоком. Изменение
файла между проверкой и потреблением отклоняется. Повторный запуск остаётся
идемпотентным. Staging каждого набора изолирован по ревизии входных данных;
ранее завершённые ревизии не перезаписываются.

## Экспорт, ingest и анализ — разные состояния

Успешное сохранение или ingest файла не означает, что он расшифрован,
эмбеддирован или проанализирован. Смотрите отдельно статусы export, ingest,
ASR и embeddings.

ASR-путь в текущем коде обрабатывает только распознаваемые voice/audio-типы.
Он ограничивает локальный аудиофайл `100 MiB`; адаптер также задаёт предел
передачи провайдеру `25,000,000` байт — это текущий консервативный предел
адаптера, который не определяет тариф аккаунта динамически. Groq публикует
разные лимиты загрузки для Free и Developer; перед изменением адаптера нужно
проверить применимый лимит аккаунта в [официальной документации Speech-to-Text](https://console.groq.com/docs/speech-to-text).
Больший файл остаётся в экспорте и базе, а ASR показывает причину пропуска.
Видео в ASR не преобразуется, аудио не режется на части; извлечение дорожки,
сегментация с временными смещениями, сбор результатов и точная связь
фрагментов с исходным сообщением требуют отдельной реализации. Не считайте
такой медиафайл проанализированным.

## Совместимость и ограничения

Пакет принимает старые обычные Telegram exports с manifest version 1 и
прежним default 100 MiB. В новых конфигурациях пути и параметры оператора
задаются вне репозитория. Доступ к истории, удалённые сообщения и события,
которые Telegram не выдаёт аккаунту/API, нельзя восстановить экспортёром;
они отмечаются неполнотой/ограничением. Реальный экспорт требует аккаунта и
внешнего Telegram CLI; автоматические тесты используют только синтетические
данные.
